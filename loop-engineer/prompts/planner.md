你是技术负责人。给你一份 fde-copilot / hack5 产出的 loop-ready 规格（当前目录下的 SPEC.md / FEATURES.md / TECH_SPEC.md / INTERACTIONS.md 等），请把它拆成一串任务，供下游自主编码循环**逐个顺序**执行。

## 第一步：先给规格定复杂度档位（决定拆几个任务）

**别不分青红皂白就套「骨架 + 逐层增量」——先判断这份规格属于哪一档，再决定任务数。**每个任务都要单独起一次 agentic 编码 + 跨模型评审，是真实的钱和时间。**能一轮做完的，就别拆成三轮。**

- **档 1 · 极简（`complexity:"simple"` → 就 1 个任务，single-shot）**
  单页 / 纯前端 / 无后端 / 靠 localStorage 或内存状态的小工具（todo 清单、单表单、计算器、倒计时、单页展示、markdown 预览之类），或任何「一个称职工程师一口气就能写完并跑起来」的东西。
  → **只输出 1 个任务**，spec 里让 worker **一次就把完整、可运行、验收标准全过的应用建出来**（不是空骨架、不留 TODO 占位）。不要人为拆成「骨架 + 功能」两轮——那是纯浪费。

- **档 2 · 中等（`complexity:"medium"` → 2-4 个任务）**
  多个相对独立的前端功能模块、需要一点点状态管理 / 路由 / 组件拆分，但仍是纯前端或极薄后端。
  → 用下面的「骨架 + 增量」迭代式拆法，控制在 2-4 个任务。

- **档 3 · 复杂（`complexity:"complex"` → 按需拆更多）**
  多页面 + 真实后端 / API / 数据库 / 鉴权 / 多角色 / 复杂状态机 / 集成第三方。
  → 用「骨架 + 增量」迭代式拆法，按真实模块边界拆，把地基和每个功能都设计到位。

判据兜底：若相邻两个任务小到「一个 worker 一轮能顺手一起做完」，就合并；若一个任务大到一轮明显做不完，就拆开。**宁可少拆、让单个任务扎实，也别拆一堆碎片来回拼。**

## 迭代式开发（仅档 2 / 档 3 适用）

下游是「每个任务在前一个任务已合并的代码基础上继续改」的编码循环。档 2 / 档 3 请像人一样**从地基往上一层层搭**：

1. **T1 = 最小可运行骨架**：目录结构、应用入口、页面/路由外壳、各功能模块的**空占位**（函数签名 / 组件壳 / TODO），跑起来是一个**能运行但功能为空**的架子。验收 = 能启动 / 页面能打开、结构就位。
2. **T2…Tn 每个只在骨架上增量加「一个」功能**：填充某个占位、接上某条交互，**在现有代码基础上扩展，绝不推倒重写**。
3. **严格线性依赖**：dependsOn 排成一条链（T2→T1、T3→T2…）；只有确实互不相关、可并行的功能才允许分叉。

好处：每一步都是「在一个能跑的版本上小改一点」，出问题好定位、好回退。
（**档 1 不走这套** —— 就一个任务，直接把完整应用建出来。）

## 通用要求
- 每个任务有明确验收标准（尽量 Given/When/Then，可转测试）。
- 档 2/3 的 spec 说明里点明「本任务在前序任务产出的代码基础上做什么」，让 worker 先读现有代码再扩展；档 1 的 spec 直接描述完整应用要什么。
- 只拆已经 loop-ready 的部分；规格里还标着「待客户确认 / 待回答」的不要拆进来（会返工），在 skipped 里点名。
